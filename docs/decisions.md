# 已确认范围与待定设计

## 已确认

- 项目名 PiMesh，成员在各端开发环境使用的命令为小写 `meshpi`。
- 基于 Pi，服务算法团队；成员和项目是多对多关系。
- 全组可以查看各项目的研究记录、实验与进度。
- 每个人使用过程中的完整 Transcript 必须持续保存，不能用摘要替代原文。
- 将实验、错误与经验、公共工具沉淀为团队资产。
- 支持管理者了解全局，未来可基于来源记录生成组周报。
- 公司内部训练提交、任务状态、日志与指标系统需要接入，可通过工具接口和 Skill 组合。
- 开发代码与文档应及时同步 GitHub；公司研究数据不进入公开源码仓库。

## 本次实施的技术选择

第一版采用 Node.js ESM，锁定 `@earendil-works/pi-coding-agent@0.84.2`，
通过独立 CLI 和显式加载的 extension 保存记录。这样能复用 Pi 原生 UI、认证、
工具和 Session 管理，避免维护另一套模型运行循环。

本地目录的哈希仅用于区分工作目录，不是未来的团队项目 ID。不同 Mac、不同 worktree
不会因此自动认作同一个项目。共享服务身份协议确定后另行映射，不把路径写死为全局身份。

原生 Session 用于继续会话；Transcript 用于保留操作历史及流式中断记录。
两者目前都保存在本地，第一版不创建共享服务、不上传数据。

## 尚未确定，不应提前视为产品承诺

- Transcript 是否全组可见、上传方式、保留与备份政策。
- 个人、项目、团队 Memory 的具体模型及相互转化规则。
- Session 小结何时生成，哪些条目自动共享，哪些需要成员确认。
- 搜索、上下文注入、知识验证、纠错、过期与版本管理。
- 服务端存储、身份认证、同步协议和离线冲突处理。
- 公司平台的实际 API、CLI、权限和所需 Skill。

之前讨论的三层 Memory 和默认私有 Transcript 是候选方案。
用户已明确 Memory 设计仍需讨论，不应把这些候选策略编码成既定规则。

## 后续验收方向

成员 A 完成工作并沉淀证据，成员 B 能找到并正确复用；管理者能从有来源的项目记录
理解进展和阻塞。具体 Memory 方案确定后，再拆分为实现任务。

## 开发协作决定（2026-09-07）

维护者确认采用各电脑独立运行 Codex、Git 同步代码与任务交接文档的方式，
避免依赖另一台电脑持续在线或预先配置任务远程连接。
一任务一份交接记录，长期决定保存于本文件，按 `docs/collaboration.md` 执行。
该约定用于开发 PiMesh 的工程上下文交接，不实现完整 Codex 对话同步，
也不改变产品 Transcript、Memory 和团队共享的待定设计。

## 默认本地目录与多端定位（2026-09-07）

默认存储根目录采用用户主目录下的 `.meshpi`，便于定位配置、凭据和会话；
绝对路径 `MESHPI_HOME` 仍可覆盖默认值。升级不自动迁移、合并或删除旧目录，
避免覆盖已有数据；需要原有状态时可显式指向旧目录。
产品面向多端开发环境，当前自动验证覆盖 macOS/Linux；Windows 原生支持尚未验证。

## 团队服务基础（2026-09-07）

测试服务器先使用系统 Node.js 22 + PostgreSQL 15，通过 systemd 管理。
API 使用 `/api/v1`，数据库连接集中配置；当前先部署健康检查，不提前选定邮箱认证方式。
默认经 SSH 隧道访问；维护者已授权测试部署开放 8080 HTTP 健康检查，后续公开业务入口配置 HTTPS。
